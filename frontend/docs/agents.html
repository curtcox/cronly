The same quoted API powers the workspace and your scripts.

Credentials and scopes

Create a key on Account. Send Authorization: ApiKey crk_…. Scopes are read, run, change, prose and secrets:write. Basic reads cost the published base price; aggregate history adds the published per-job scan allowance, reserved before reading logs. API keys may have UTC daily spend caps and expire within one year. Sessions can manage keys and deposits; delegated keys cannot. Use the pricing page for current read and operation prices.

Quote, review, apply

curl -X PUT 'https://cronly.org/api/variables/base-url?dry_run=1' \
 -H 'Authorization: ApiKey YOUR_KEY' \
 -H 'Content-Type: application/json' \
 -d '{"value":"https://api.example.com"}'

curl -X PUT 'https://cronly.org/api/variables/base-url' \
 -H 'Authorization: ApiKey YOUR_KEY' \
 -H 'Content-Type: application/json' \
 -H 'Idempotency-Key: set-base-url-v1' \
 -d '{"value":"https://api.example.com"}'

Dry runs validate and return quote_microdollars without changing or charging. Applying is a separate request. Idempotency keys are limited to 128 characters; reuse only for the same intent. All money is integer micro-dollars. 402 reports insufficient balance or budget; 409 reports conflicting idempotency, stale proposals or overlap; 429 reports rate limits. Do not loop on a 402.

Account as code

GET /api/config exports variables, actions, jobs and secret metadata. PUT /api/config?dry_run=1 validates a diff, then PUT applies it atomically. Omitted collections remain unchanged; supplied collections replace that collection. Secret values must be created through the write-only secret endpoint. Removing a secret requires secrets:write. A repeated import with the same idempotency key returns its original result, including a no-op import, even after later account edits. Changed documents need a new key. Dry runs always quote the current account and do not consume the key.

Prose

Use /api/prose/to-cron, /ask or /change with JSON {"text":"…","timezone":"UTC"}. Quote the maximum first. Translation explanations are regenerated from cron. Questions use read-only tools scoped to this account. Changes return a proposal, concrete operations, normalized before/after diffs from the reserved account snapshot, an explanation, expiry and a server application quote. The prose charge is separate from that application quote. A separate POST /api/changes/{id}/apply applies it. Any intervening configuration change makes it stale. Never treat model text as authorization.

Remote MCP

Endpoint: https://cronly.org/mcp, Streamable HTTP with the API-key Authorization header. Stateless JSON responses, protocol 2025-11-25. Initialize, send notifications/initialized, then tools/list or tools/call. GET returns 405 because this server does not provide an SSE stream. Foreign Origin headers are rejected.

Tools: list_jobs, upcoming, recent_runs, get_run, explain_cron, prose_to_cron, quote, apply_change, run_job, balance. Each tool uses the same ordinary API and scopes. apply_change requires the reviewed quote_microdollars and checks it again before applying.

Browser triggers

Create a trigger token in a job editor. It can only run that job and may be revoked. Each token has a per-minute rate limit; the job also has a one-run-per-minute limit and its normal budgets. Never place an API key in a public page.

The immutable SDK is /sdk/v1/cronly.js; get its SHA-384 SRI value from integrity.json. Load it as a classic script with that integrity attribute and crossorigin="anonymous".

<script src="https://cronly.org/sdk/v1/cronly.js"
 integrity="COPY_FROM_INTEGRITY_JSON" crossorigin="anonymous"></script>

// Run from your page's own script:
await cronly.trigger('tk_…', { message: 'hello' });

CORS is open for hook requests and the public SDK asset, never for authenticated account APIs. Costs accept UTC date windows up to 366 days. Upcoming windows are bounded to 31 days and results indicate truncation. Use transactions' next_cursor to page permanent billing history. The unfiltered runs feed returns compact summaries across up to 100 recently run jobs. Filter by job for full logs, up to 100 per page; send cursor=next_cursor with the same job and filters for the next page. Cursors include a stable tie breaker so immediate retries sharing a timestamp are not skipped. NDJSON uses the same paging, with X-Next-Cursor in its response headers. Legacy before=next_before timestamp paging remains supported.
